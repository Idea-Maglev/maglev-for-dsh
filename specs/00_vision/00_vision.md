# Maglev for DSH Vision

> **Vision**: 让 Maglev 的研发对齐方法成为 dsh 生态里一个"装上即用、看得见、可自证"的插件——软件研发团队和个人装上它，就能做长期可控的迭代，迭代中天然沉淀知识资产，降低对特定人和 AI 体系的依赖。

## 1. 我们在构建什么

一个**自包含的 dsh 插件制品**，它把 Maglev 的协议层（技能 + 知识分层）与 dsh 的执行层（agent 循环、工具、沙箱、会话日志）结合，并新增产品化的 GUI（把抽象的知识资产与迭代进度可视化）。

它由三层构成：

1. **技能层**：29 个固化的 Maglev 技能（收敛→设计→验证→结晶主链路 + 治理 + 知识）
2. **插件层**：dsh host 插件（spec 工具、结晶事件）+ client 插件（Maglev 面板、结晶卡片）
3. **资产层**：preset（对齐模式）、workflow（主链路编排）、验证脚本

## 2. 我们要解决什么问题

dsh 提供强大的执行能力，但缺少软件研发的**流程语义**：需求→设计→验证的阶段门、验收证据、不可变 Spec、流程纪律都不存在。Maglev for DSH 补上这一层，让 dsh 用户在"写代码更快"之外，获得"交付更稳、知识沉淀、长期可控"。

## 3. 北极星原则（继承 Maglev）

1. **Spec First**：关键变更先形成可执行 Spec，再进入实现与验证。
2. **Observe Before Act**：先基于仓库现实判断，再执行。
3. **Think Before Code**：设计依据显性化，不依赖口头背景。
4. **Verify Before Closeout**：交付必须经过验证闭环，再收口。

## 4. 自证原则（本仓库的立身之本）

Maglev 用自己构建自己，用自己治理自己。本仓库本身就是 Maglev 机制的实例——它的演进走 Maglev 主链路，知识沉淀在 `specs/` 三层。只有本仓库自己跑通了闭环，才有资格论证插件有效。

## 5. 我们不是什么

- 不是 [Maglev 上游仓库](https://github.com/Idea-Maglev/maglev) 的镜像或运行时依赖方（零依赖，派生分叉）
- 不是 dsh 的替代品（dsh 是执行层宿主，Maglev 是流程语义）
- 不是又一个"让 AI 多写代码"的工具（目标是可控、沉淀、降依赖）
